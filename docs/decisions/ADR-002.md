# ADR-002: Package layout, plug-in discovery and generated schemas

- **Status:** Accepted
- **Requirements:** BRD 11, FR-ENG-05, FR-API-08, BRD 7.7, AC-ENG-03/04

## Context
BRD Section 11 places domain packages in a top-level `domains/` folder beside
`src/simcore/`. Core must discover domains without importing them.

## Decision
- `src/` layout for `simcore`; `domains` is a second top-level import package in
  the same distribution (hatch `packages = ["src/simcore", "domains"]`).
- Domains are discovered through the `simcore.domains` entry-point group
  (`module:attribute` → `DomainPlugin` instance or class). Explicit loading by
  `module:attr` (`--plugin`) is also supported for out-of-tree domains.
- Everything a plug-in registers (policies, KPIs, disruption types, params
  schema) is looked up *per domain*, so two plug-ins never collide in one process.
- Spec contracts are Pydantic v2 models in `simcore.specs`. JSON Schemas in
  `schemas/` are **generated** (`make schemas`) and checked in; a test fails if
  they drift from the models. Frontend TS types and LLM tool schemas will be
  generated from these files (M7/M10/M11).
- Import rules are enforced by import-linter (contracts in `pyproject.toml`) plus
  an AST test and a domain-vocabulary scan of `core/`.

## Consequences
- The name `domains` is generic; if this ever ships to PyPI it should be renamed
  (e.g. `simcore_domains`). Only `pyproject.toml` and imports in tests change.
- `simcore.core` may depend on `simcore.specs` (and vice versa only for
  `core.units`/`core.hashing`, which import nothing else).
