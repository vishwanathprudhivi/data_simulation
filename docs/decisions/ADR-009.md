# ADR-009: Redis queue encoding, plan execution, solver callbacks (M5)

- **Status:** Accepted
- **Requirements:** FR-DSP-02/05/06, FR-POL-02/05, FR-IFC-03, AC-DSP-01/02

## Decisions
- **RedisQueue.** Pending tasks live in a sorted set (score 0) ordered
  lexicographically by `inverted priority (8 hex) | release time (16 hex,
  order-preserving IEEE-754 encoding) | sequence (12 hex) | id`. Claim is one Lua
  script (atomic); in-flight entries record a claim counter so `in_flight()` keeps
  claim order. Keys are namespaced per queue instance (random namespace: isolation
  only, never affects order). The shared conformance suite runs against both
  queues; an engine run on Redis produces the same event log as in-memory.
  Selection: `--queue redis://...` / `run_scenario(queue=...)`; in-memory default.
- **Plans** are a new spec contract, `PlanSpec` (agent -> ordered tasks with optional
  planned start/finish, an `unplanned` fallback, and expected KPIs). The
  `plan_follower` policy gives each agent its next planned task as soon as that
  task is released and otherwise leaves the agent idle; tasks/agents outside the
  plan use `fifo` unless `unplanned: none`. After the run the policy contributes
  adherence KPIs (`plan_on_agent_rate`, `plan_sequence_adherence`,
  `plan_start_deviation_mean`, ...) and a `policy_report` in `meta.json` comparing
  realized KPIs with `expected_kpis`.
- **Policy hooks.** `Policy.kpi_calculators()` and `Policy.report(kpis)` are optional
  extension points used by the engine for any policy.
- **Solver callbacks.** `solver_callback` calls a deterministic `module:function`
  with `(observation, params)` returning `(agent, task)` pairs, validated like any
  policy output. Built-in example: `assignment_min_distance` (Hungarian, SciPy).
- **Evaluator** accepts `plan=` (dict or `PlanSpec`); plans are normalised before
  hashing so the cache key is independent of how the plan was supplied.
